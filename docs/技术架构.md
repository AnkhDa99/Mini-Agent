## 1. 项目概述

Mini Agent 是一个面向 **IT 运维排障场景** 的智能 Agent 系统。用户上传运维文档（PDF/Word/PPT 等），系统构建可检索的知识库。当用户提出运维问题时，Agent 自动分类问题、选择检索策略、在文档库和场景知识库中搜索相关信息，最终生成带来源标注的回答。

**核心能力：**
- 支持 8 大运维场景（MySQL/Redis/K8s/Nginx/Kafka/ES/Docker/Java）
- 两层智能分类（深度 + 复杂度），12 种策略组合
- 多路融合检索（FAISS 向量 + ES 关键词 + Concentration-RRF）
- ReAct Agent 循环（Think → Act → Observe → Critic）
- 三级降级链 + 联网搜索兜底
- 场景知识图谱（Neo4j 图数据库 + FAISS 语义匹配）
- 文档生成（PPT/Word/PDF/Excel/Diagram/Markdown）

## 3. 核心技术链路：从提问到回答

```
用户提问: "我们Redis集群最近频繁OOM，怎么排查？"
  │
  ├─[Step 1] 文档意图检测
  │   检测用户是否要求生成文档(PPT/Word/PDF/Excel/Diagram/Markdown)
  │   本例: 无文档生成意图 → 继续
  │
  ├─[Step 2] Layer 1 分类: classifier.py
  │   正则预检 → 非闲聊 → LLM 分类
  │   结果: DEEP (需要综合多文档分析推理)
  │   → max_rounds=5, 全部工具可用, degradation_max_level=2
  │
  ├─[Step 3] 场景知识库检索: scenario_matcher.py
  │   query → embedding → FAISS 语义匹配
  │   命中: "Redis 内存满 OOM 故障排查" (score=0.85)
  │   → Neo4j 图谱扩展: 召回关联的 "Redis 持久化配置" "内存优化策略"
  │   → 场景感知关键词: [Redis, OOM, 内存, maxmemory]
  │
  ├─[Step 4] Layer 2 分类: query_classifier.py
  │   正则匹配 → "怎么排查" → ANALYTICAL
  │   → 检索管道: Full + Multi-Query + HyDE + RRF
  │
  ├─[Step 5] 本地文档检索: search_router.py → _route_analytical()
  │   ① 原始 query → FAISS + ES → Concentration-RRF
  │   ② Multi-Query 生成 2-3 个变体 → 多路检索
  │   ③ HyDE 生成假设文档片段 → 向量检索
  │   ④ Score-based 融合多轮结果
  │   ⑤ 场景感知过滤: 保留含 [Redis/OOM/内存/maxmemory] 的文档
  │
  ├─[Step 6] 质量评估: critic.py
  │   集中度 concentration = 0.65 → good (>=0.5)
  │   → 进入 Agent 循环
  │
  ├─[Step 7] Agent 循环: agent_loop.py
  │   Round 1: Think → Act(search_knowledge_base) → Observe → Critic(CONTINUE)
  │   Round 2: Think → Act(analyze_retrieval_signals) → Observe → Critic(STOP)
  │   → 信息充足，生成最终回答
  │
  └─[Step 8] 生成回答
       基于检索结果 + LLM 整合 → 带来源标注的回答
       标注: [项目文档] [知识库] [通用知识] [网络搜索]
```

## 4. 第一层分类：QueryClass（问题深度）

**文件**: `app/agent/classifier.py`

决定 **"用多少工具、最多搜几轮、降级到哪一层"**。

```
输入: 用户原始问题文本
输出: ClassificationResult(query_class, max_rounds, allowed_tools, degradation_max_level, ...)
```

### 分类流程

```
用户问题
  │
  ├─ 正则预检 (1ms)
  │   匹配 CHITCHAT_PATTERNS (你好/谢谢/再见/在吗/哈哈...)
  │   命中 → CHITCHAT, confidence=1.0, 跳过 LLM
  │
  └─ LLM 分类 (~300ms)
      输入: CLASSIFIER_SYSTEM_PROMPT + 问题
      输出: {"class": "chitchat|shallow|deep", "reason": "..."}
      失败兜底: SHALLOW (保守策略)
```

### 三类问题的处理策略

| 分类 | 触发条件 | max回合 | 工具类别 | 降级级别 | 典型问题 |
|------|---------|---------|---------|---------|---------|
| **CHITCHAT** | 问候/感谢/闲聊 | 1 | 无 | 0 | "你好" "谢谢" |
| **SHALLOW** | 单一概念/简单对比/参数查询 | 2 | search+mcp | 2 | "什么是Redis" "MySQL端口" |
| **DEEP** | 综合分析/方案设计/文档生成 | 5 | 全部(15个) | 2 | "设计微服务架构方案" |

**关键设计**：
- CHITCHAT 完全跳过检索，直接 LLM 回答，节省 ~500ms
- SHALLOW 有联网搜索能力（degradation_max_level=2），但不主动触发
- DEEP 全能力开放，含文档生成工具（PPT/Word/PDF/Excel/Diagram/Markdown）

## 5. 第二层分类：QueryComplexity（检索复杂度）

**文件**: `app/services/query_classifier.py`

决定 **"用哪种检索管道、是否扩展检索、是否精排"**。

```
输入: 用户原始问题文本
输出: ClassificationResult(complexity, needs_expansion, needs_rerank, needs_plan_execute, ...)
```

### 分类逻辑

```
用户问题
  │
  ├─ 正则快速判断 (SIMPLE_PATTERNS → FACTUAL_PATTERNS → COMPLEX_PATTERNS → ANALYTICAL_PATTERNS)
  │   按优先级依次匹配，命中即返回
  │
  ├─ 启发式兜底
  │   长度 < 10 → FACTUAL (confidence=0.5)
  │
  └─ LLM 细粒度分类
      短文本输出: simple | factual | analytical | complex
      失败兜底: ANALYTICAL (confidence=0.3)
```

### 四类检索复杂度

| 复杂度 | 检索管道 | 扩展检索 | 精排 Reranker | Plan-Execute | 典型问题 |
|--------|---------|---------|-------------|-------------|---------|
| **SIMPLE** | ES-only | 无 | 无 | 无 | "你好" "Redis" |
| **FACTUAL** | ES+FAISS+RRF | 无 | 无 | 无 | "什么是Redis" "MySQL默认端口" |
| **ANALYTICAL** | Full+MultiQ+HyDE+RRF | MultiQ+HyDE | 可选 | 无 | "Redis内存满了怎么办" |
| **COMPLEX** | Plan-Execute+Reranker | 子查询拆解 | 有 | 有 | "设计微服务架构方案" |

### 两层分类的关系

```
Layer 1 (深度)          Layer 2 (复杂度)        实际效果
─────────────────────────────────────────────────────────
CHITCHAT      ──→      (不触发 L2)         直接回答，0检索
SHALLOW       ──→      SIMPLE/FACTUAL      2轮限制，轻量检索
SHALLOW       ──→      ANALYTICAL/COMPLEX  2轮限制 + 扩展检索
DEEP          ──→      FACTUAL             5轮限制，基础检索即可
DEEP          ──→      ANALYTICAL          5轮限制 + 全能力扩展
DEEP          ──→      COMPLEX             5轮限制 + Plan-Execute
```

**两层独立运行**：L1 控制"量"（轮次、工具），L2 控制"质"（管道、策略）。两两组合产生 12 种策略配置。

## 6. 检索管道详解

**文件**: `app/services/search_router.py`

SearchRouter 根据 L2 分类结果，将查询路由到 4 种不同的检索管道。

### 管道 1: SIMPLE → ES-only（~10ms）

```
query → ES 关键词搜索 → top_k 返回
```

- 仅用 Elasticsearch BM25 关键词匹配
- 无向量检索、无融合、无扩展
- 适用场景：单关键词、极短查询

### 管道 2: FACTUAL → ES + FAISS + Concentration-RRF（~200ms）

```
query → embedding
  ├─ FAISS 向量检索 (k=25)
  └─ ES 关键词检索 (k=25)
       ↓
  chunk 去重加载 (owner_id 数据隔离)
       ↓
  Concentration-RRF 融合
       ↓
  top_k=10 返回
```

- **Concentration-RRF** 自适应融合算法
  - 计算文档集中度（多结果是否集中在同一文档）
  - 集中度高 → FAISS 权重提升
  - 集中度低 → ES 权重提升
  - RRF 公式: `score(d) = SUM(1/(k+rank_i(d))), k=60`

### 管道 3: ANALYTICAL → Full + MultiQ + HyDE（~500ms）

```
query → Multi-Query 扩展 (LLM, 2-3 变体)
  ├─ Round 0: query → HyDE(LLM生成假想文档) → FAISS + ES → RRF
  ├─ Round 1: variant_1 → FAISS + ES → RRF  (weight=0.6)
  └─ Round 2: variant_2 → FAISS + ES → RRF  (weight=0.6)
       ↓
  Score-based 多轮融合 (取 max rrf_score)
       ↓
  可选 Reranker 精排 (仅 concentration 低时)
       ↓
  top_k=10 返回
```

- **Multi-Query**: LLM 从不同视角改写查询（如："Redis OOM 原因" → 变体["Redis 内存溢出排查", "Redis maxmemory 配置优化"]）
- **HyDE** (Hypothetical Document Embeddings): LLM 先生成一段假设的文档内容，用该内容做向量检索，解决 query 与文档用词不一致的问题
- **超时保护**: 整体 deadline 控制，超时降级为 FACTUAL

### 管道 4: COMPLEX → Plan-Execute + Reranker（~2-5s）

```
query → LLM Plan: 拆解为 2-3 个子问题
  ├─ Sub-query 1 → _route_factual() → 结果集 A  (10s 超时)
  ├─ Sub-query 2 → _route_factual() → 结果集 B  (10s 超时)
  └─ Sub-query 3 → _route_factual() → 结果集 C  (10s 超时)
       ↓
  Aggregation: 按 chunk_uid 取 max rrf_score 合并
       ↓
  BGE Reranker 精排 (reranker_enabled=True 时)
       ↓
  top_k=10 返回
```

- **Plan-and-Execute**: LLM 将复杂问题拆解为独立的原子问题
- **子查询隔离**: 每个子查询独立走 FACTUAL 管道，有 10s 独立超时
- **降级链**: Plan 失败 → ANALYTICAL，超时 → FACTUAL
- **子查询上限 3 个**，避免递归爆炸

### 融合信号说明

每次检索输出的 `fusion_info` 包含：

| 信号 | 含义 | 用途 |
|------|------|------|
| `faiss_ok` | FAISS 检索是否正常 | 诊断 |
| `es_ok` | ES 检索是否正常 | 诊断 |
| `faiss_conc` | 文档集中度 (0-1) | 质量评估核心指标 |
| `faiss_top1_cosine` | top-1 余弦相似度 | 语义匹配强度 |

## 7. 搜索优先级链路

这是整个系统最核心的决策流程，决定了"什么时候搜什么"。

```
用户提问
  │
  ├─[1] CHITCHAT 拦截
  │     └─ 跳过全部检索 → 直接 LLM 回答
  │
  ├─[2] 文档生成意图检测
  │     检测: PPT/Word/PDF/Excel/Diagram/Markdown
  │     └─ 命中 → 检索 → 文档生成工具 → 回答
  │
  ├─[3] 场景知识库检索 ── 优先！
  │     └─ FAISS 语义匹配 + Neo4j 图谱扩展
  │         ├─ 命中 (score >= 0.6) → 场景关键词过滤本地文档
  │         └─ 未命中 → 本地文档无额外过滤
  │     (scenario_kb_enabled=False 时跳过此步)
  │
  ├─[4] 本地文档检索
  │     └─ SearchRouter 按 L2 复杂度路由
  │         SIMPLE → ES-only
  │         FACTUAL → ES+FAISS+RRF
  │         ANALYTICAL → Full+MultiQ+HyDE+RRF
  │         COMPLEX → Plan-Execute+Reranker
  │
  ├─[5] 质量评估 (concentration-based)
  │     ├─ good (>=0.5)    → Agent 循环 → 生成回答
  │     ├─ marginal (0.3-0.5) → 继续但可选扩展检索
  │     ├─ poor (<0.3)    → 进入降级/联网路径
  │     └─ empty (0 结果) → [跨语言改写重试] → 仍空则降级
  │
  ├─[6] 降级/联网路径 (quality = empty/poor)
  │     ├─ force_web_search = TRUE
  │     │   └─ 直接联网搜索 + LLM 整合 → 回答 [网络搜索]
  │     │
  │     └─ force_web_search = FALSE
  │         ├─ CHITCHAT (max_level=0) → 仅诚实声明
  │         ├─ SHALLOW (max_level=2)  → Level 0+1+2
  │         └─ DEEP (max_level=2)     → Level 0+1+2
  │
  └─[7] Agent 循环 (仅在第5步本地有结果时触发)
        └─ Think → Act → Observe → Critic → 终止判断
```

### 关键决策规则

| 场景 | 行为 |
|------|------|
| CHITCHAT 问题 | 不检索，不联网，直接回答 |
| SHALLOW + 本地有结果 | Agent 循环 (最多2轮) + 生成回答 |
| DEEP + 本地有结果 | Agent 循环 (最多5轮) + 生成回答 |
| SHALLOW/DEEP + 结果差 + 已勾选联网 | 绕过降级链，直接联网搜索 |
| SHALLOW + 结果差 + 未勾选联网 | 降级链: 诚实声明 → LLM知识 → 联网兜底 |
| DEEP + 结果差 + 未勾选联网 | 降级链: 同上，含联网搜索兜底 |
| 场景KB命中(≥0.6) | 场景关键词严格过滤本地文档 |
| 场景KB未命中 + 低集中度 | `_filter_results_by_quality` 过滤尾噪 |

## 8. Agent 循环（ReAct）

**文件**: `app/agent/agent_loop.py`

ReAct (Reasoning + Acting) 模式：Agent 在每轮中思考 → 行动 → 观察 → 自检，直到信息充足。

### 循环流程

```
Round 1:
  Think: LLM 分析问题 + 检索信号 → 决定调用什么工具
  Act:  执行工具 (search_knowledge_base / search_scenario_kb / ...)
  Observe: 收集工具返回的结果
  Critic: 评估检索质量 + 信息增益 → CONTINUE / STOP

Round 2:
  Think: 评估上一轮结果 → 决定是否换策略
  Act:  rewrite_query / hyde_search / web_search / ...
  Observe: 合并结果
  Critic: 评估 → CONTINUE / STOP

...直到终止条件触发
```

### 四层终止条件（按优先级）

| 层级 | 条件 | 说明 |
|------|------|------|
| **L1** | round > max_rounds | 硬上限 (chitchat=1, shallow=2, deep=5) |
| **L2** | 连续 2 轮未调检索工具 | Agent 在生成答案而非检索 |
| **L3** | 连续 2 轮 info_gain < 20% | 信息增益衰减，继续搜索无意义 |
| **L4** | 连续 2 轮 Critic STOP | 模型自判信息已充分 |

### AgentState 状态追踪

```python
@dataclass
class AgentState:
    user_query: str                # 原始问题
    classification: L1Result      # Layer 1 分类结果
    round: int = 0                # 当前轮次
    max_rounds: int = 1           # 最大轮次

    # 检索状态
    search_results: list[dict]    # 当前检索结果
    seen_chunk_uids: set[str]     # 已见过的 chunk (去重)
    fusion_info: dict | None      # 检索融合信号
    last_info_gain: float         # 上一轮信息增益
    all_results: list[dict]       # 累积所有轮次的结果

    # 终止信号计数
    consecutive_non_search_rounds: int
    consecutive_low_gain_rounds: int
    consecutive_stop_decisions: int

    # 场景匹配
    scenario_matches: list[dict]  # 场景 KB 匹配结果
    scenario_match_score: float   # 最高匹配分数

    # 降级
    degradation_triggered: bool
    degradation_result: DegradationResult | None

    # 联网搜索
    force_web_search: bool        # 前端是否勾选联网
    final_answer: str             # 最终回答
```

## 9. 降级链（Degradation Chain）

**文件**: `app/agent/degradation.py`

当文档库完全无结果、或结果质量极差（poor/empty）时触发。

### 三级降级

```
文档库无结果 / 质量极差
  │
  ├─ Level 0: 诚实声明 (必须)
  │   "项目文档库中未找到与您问题相关的内容。"
  │
  ├─ Level 1: LLM 自身知识
  │   基于 LLM 训练数据回答问题
  │   标注: [通用知识]
  │
  └─ Level 2: 联网搜索 (max_level >= 2 时)
      ① DuckDuckGo / Brave Search 搜索
      ② LLM 整合搜索结果
      ③ 标注: [网络搜索]
      ④ 末尾追加参考来源 URL
```

### 降级级别与分类的对应

| 分类 | degradation_max_level | 实际效果 |
|------|----------------------|---------|
| CHITCHAT | 0 | 仅诚实声明，不回答 |
| SHALLOW | 2 | Level 0+1+2 全部可用 |
| DEEP | 2 | Level 0+1+2 全部可用 |

### 特殊路径

**force_web_search = TRUE** 时，跳过降级链的渐进流程，直接执行联网搜索 + LLM 整合。此路径的优先级高于降级链。

## 10. 场景知识库 + Neo4j 知识图谱

### 场景知识库

**文件**: `app/services/scenario_matcher.py`

独立的 FAISS 知识库，存储结构化运维故障排查知识卡片。

**数据结构**:
```
KnowledgeEntry (MySQL)
  ├─ entry_uid: 唯一标识
  ├─ template_uid: 所属模板 (如 Redis故障排查)
  ├─ title: 标题 ("Redis 内存满 OOM 故障排查")
  ├─ content: Markdown 内容
  ├─ tags: "Redis,OOM,内存,缓存,maxmemory"
  ├─ status: "approved" / "pending"
  └─ is_active: 是否启用 (停用模板的所有条目不参与检索)
```

**检索流程**:
```
query → embedding → FAISS 语义匹配 (top_k=5)
  │
  ├─ 候选人过滤: status=approved + template.is_active=True
  │
  └─ Neo4j 图谱扩展
       │
       ├─ RELATED_TO: 强相关 → +0.05 score boost
       ├─ SIMILAR_TO: 相似 → +0.03
       ├─ CAUSED_BY: 根因 → +0.04
       ├─ PREREQUISITE_OF: 前置知识 → +0.02
       └─ ACCOMPANIED_BY: 伴随 → +0.02
       │
       └─ 按 similarity_score 排序 → threshold 过滤 (>=0.55) → top_k 返回
```

### Neo4j 知识图谱

**文件**: `app/core/neo4j.py`

5 种关系类型连接知识条目：

| 关系类型 | 含义 | 示例 |
|---------|------|------|
| RELATED_TO | 强相关 | Redis OOM ←→ Redis 内存优化 |
| CAUSED_BY | 因果关系 | Redis OOM → 大Key未设置过期 |
| PREREQUISITE_OF | 前置知识 | 内存模型 → OOM 排查 |
| SIMILAR_TO | 相似问题 | Redis OOM ∼ Redis 内存碎片 |
| ACCOMPANIED_BY | 伴随现象 | Redis OOM + 延迟升高 |

### 场景感知过滤

当场景 KB 匹配到高置信度结果 (score >= 0.6) 时，提取场景关键词（如 tags 中的词），对本地文档检索结果做 **严格关键词过滤**：
- 文档内容含场景关键词 → 保留
- 文档内容不含场景关键词 → 过滤掉

这确保了当用户问 "Redis OOM" 时，Nginx/MySQL 等无关运维文档不会混入结果。

### Agent 扩展点

SearchRouter 暴露了以下扩展接口供 Agent 自定义：

```python
# 注册自定义检索策略
SearchRouter.register_strategy(name, strategy_fn)

# 注入任务规划器（用于 COMPLEX 路径的 Plan 拆解）
SearchRouter.set_planner(planner)

# 覆盖路由决策（Agent 可强制指定管道）
SearchRouter.override_route_hook(ctx) → SearchContext | None

# 检索后处理（Agent 可对结果做额外处理）
SearchRouter.post_search_hook(ctx) → SearchContext
```

QueryClassifier 同样开放扩展：

```python
# 注入自定义分类逻辑（优先级高于正则和 LLM）
QueryClassifier.classification_hook(query) → ClassificationResult | None
```
